# Road speckling diagnosis

**Finding: hard-edged, approximately 10 cm wide road-marking geometry aliases into isolated pale pixels in the aerial view. Confidence: high. No runtime files changed.**

Both the accepted four-mesh street patch and the expanded seven-mesh candidate reproduce it. Recoloring only the GLB marking material red recolors the apparent pale speckles red. Hiding that batch removes the pale pixels but reveals small darker gaps where pavement was cut around the paint. The road itself must stay opaque in any fix.

All fourteen captures completed without page errors. Browser processes are closed. Tests used request interception and temporary live material/layer changes in isolated browser contexts. No runtime asset, source file, kerb or marking position was edited.

## What does not remove the speckles

The expanded-asset tests individually removed procedural road grain, old Vidhana road/lane layers, basemap transportation, the district shadow receiver, and all flat map layers. None removed the pale road pattern. Polygon offset `(factor=0, units=-1)` and `(factor=-1, units=-1)` also did not remove it. These results do not support a basemap depth conflict, shadow-ground overlap or noisy aggregate texture as the cause of this specific pattern.

A mask of 937 red-marking pixels in the frontage road band was used for comparison. Of those positions, 933 were pale in baseline, 0 when marking material was red, and 8 when it was hidden. Texture/layer/offset interventions retained 918 to 937 pale pixels. Traffic moves between screenshots, accounting for some small count differences. This is raw image analysis, not photometric measurement.

For these long thin strip triangles, minimum triangle altitude measures their narrow dimension. The expanded marking batch also contains four degenerate/collapsed triangles; they should be cleaned during export, but cannot explain the widespread dots. The accepted marking batch has none and still shows the same aliasing.

## Minimal fix proposal

Add screen-space coverage filtering specifically to the marking material, preserving original marking boundaries, widths, positions and kerb geometry. Keep output opaque. At fractional pixel coverage, mix paint with the correct underlying pavement color/material response rather than making the marking fragment transparent into its existing cutout. This likely needs a per-marking triangle attribute identifying its adjacent/underlying pavement material, or an equivalent source-authored coverage representation. The concrete frontage and darker asphalt elsewhere must not share one guessed fallback color.

A bounded next implementation should preserve the current material batching and draw count, avoid shifting world geometry, and compare road-level line shape plus moving aerial stability. Measure frame time only after visual acceptance. Preserve clear close-range zebra crossings and lane paint; apply coverage to boundaries, not an unconditional distance hide.

Implementation caveat: naive per-triangle barycentric edge fading would expose
internal triangulation seams. Filtering only inside the current polygon cannot
provide coverage in neighboring pixels outside its rasterized boundary. A real
solution needs exterior-boundary data with adequate coverage geometry, or a
filtered raster coverage representation shared by pavement and paint. Near-view
marking width and continuous underlying pavement must both be verified; mixing
everything toward one guessed asphalt colour is not accepted antialiasing.

Do not ship the diagnostic marking hide, red recolor, global transparency fade, or polygon offset. A global MSAA switch also needs its own performance decision; this investigation did not change it or benchmark a replacement filter. Current diagnosis is complete, but the proposed coverage filter is not implemented or performance-approved.
