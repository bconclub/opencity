# Player data foundation

Status: foundation files plus the owner-supplied public project URL/key in `supabase-config.json`. No project was created. Applying migrations and enabling Anonymous Auth still require access to that existing project.

1. Wait for the owner to supply their existing Supabase project and public key. Do not create a project. Then apply `migrations/202609100001_player_foundation.sql` in SQL editor or CLI. This is a one-time migration, not a repeatable setup script.
2. Enable the desired Supabase Auth provider. Anonymous sign-in can support guests, but a multiplayer socket player ID is not an Auth user ID. Enable Auth rate limits/CAPTCHA before public guest signups.
3. Import `installPlayerStats` from `player-stats.js` after the app scripts. Call once with `{url: 'https://YOUR_PROJECT.supabase.co', publishableKey: 'YOUR_PUBLIC_KEY'}`. Omit configuration for local-only stats. Never put a secret/service-role key in public files.
4. Pass the actual Auth access token to `await playerStats.setSession(session.access_token)` on sign-in/refresh and `setSession(null)` on sign-out. Directly supplied tokens stay in memory in this module; the Auth integration owns refresh. The optional explicit `connectCloud(name)` uses pinned Supabase JS 2.57.4 to retain/refresh a guest session in browser storage. `restoreCloud()` only restores an existing session and never creates a user. Disabled anonymous sign-in, network and missing-table errors surface instead of pretending cloud sync worked. `setSession` verifies the user against Supabase Auth, not a decoded client claim.
5. Save `{displayName, favoriteVehicle}` with `saveProfile`. Read cloud aggregates via authenticated REST `/rest/v1/player_vehicle_stats`; the view respects caller RLS. `stats()` reports this-browser history, not cross-device totals.

Current auto/helicopter mode hooks are sampled every 500ms. Unpaused visible play counts toward active seconds; takeoff/flying/landing count flight seconds. Distance is integrated from reported speed, an estimate, not authoritative scoring. Future cycle/drone modes need additional state adapters. A 10-second checkpoint bounds normal abrupt-close loss; pagehide checkpoints immediately. Background stalls and pauses do not accrue time.

Ride rows are stored under individual UUID keys in localStorage, survive reload, and upload idempotently every 30 seconds when configured, signed in and online. History stops recording new sessions at 1,000 local rows rather than silently discarding unsent records. `exportHistory()` exports this device's records; `clearSyncedHistory()` removes only the current user's finished uploaded rows. Erasing browser data erases unuploaded history. Storage-denied/quota errors are reported through `stats()` and `player-stats-status` events. Local guest history remains local; it is not silently reassigned when a user signs in. Accounts never upload another account's queue.

Profiles and ride history are owner-only. Published meetup metadata is public; drafts are host-only. Registrations are readable by the attendee and event host, writable by the attendee. There is no global admin bypass or contact information in this schema. Private invitation codes must remain in the realtime backend, not public event descriptions. Events/RSVP forms and admin UI are intentionally deferred.

Before enabling cloud writes, verify with two real Auth test users: A cannot read/update B's profile or rides; guests cannot read private tables/drafts; non-hosts cannot edit meetups; attendees cannot register someone else; the host can read registrations only for their own meetup. SQL policy behavior has not been executed against a live Supabase project here. Client-recorded stats are user-editable and unsuitable for competitive rewards until verified server-side.


Optional UI wrapper: `connectPlayerCloud(stats, config)` from `player-cloud.js` exposes `connect()` (explicit user action), `restore()` (existing session only), and `meetups.list/create`. It wires the existing meetup UI hook. Published meetup host display names are intentionally public event metadata, separate from private profiles. Current created events last one hour and store an expected attendance of 1–8. Event-to-private-room association and RSVP UI remain deferred; no room invite codes are published.
